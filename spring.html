Spring



Spring framework makes the easy development of JavaEE application. 
The Spring framework comprises several modules such as IOC, AOP, DAO, Context, ORM, WEB MVC etc.

Inversion Of Control (IOC) and Dependency Injection:

These are the design patterns that are used to remove dependency from the programming code. 
They make the code easier to test and maintain.

Inversion of Control is a principle in software engineering by which the control of objects or portions of a
program is transferred to a container or framework.
Inversion of Control can be achieved through various mechanisms such as: Strategy design pattern, Service Locator pattern, Factory pattern, 
and Dependency Injection (DI).

Dependency injection is a pattern through which to implement IoC, where the control being inverted is the setting of object's dependencies.

IoC container:

In the Spring framework, the IoC container is represented by the interface ApplicationContext. 
The Spring container is responsible for instantiating, configuring and assembling objects known as beans, 
as well as managing their lifecycle.
In order to assemble beans, the container uses configuration metadata, which can be in the form of XML configuration or annotations.

Autowiring: 

Spring @Autowired annotation is used for automatic dependency injection.

Autowiring feature of spring framework enables you to inject the object dependency implicitly. It internally uses setter or constructor injection.

@Autowired annotation can be applied on variables and methods for autowiring byType. We can also use @Autowired annotation on constructor for constructor based 
spring autowiring.

@Qualifier annotation – This annotation is used to avoid conflicts in bean mapping and we need to provide the bean name that will be used for autowiring. 
This way we can avoid issues where multiple beans are defined for same type. This annotation usually works with the @Autowired annotation. 
For constructors with multiple arguments, we can use this annotation with the argument names in the method.

3. What is Dependency Injection?

Inversion of Control (IoC) is a general concept, and it can be expressed in many different ways and Dependency Injection is merely one concrete example of 
Inversion of Control.

This concept says that you do not create your objects but describe how they should be created. You don't directly connect your components and services 
together in code but describe which services are needed by which components in a configuration file. A container (the IOC container) is then responsible 
for hooking it all up.

6. What are the different types of IoC (dependency injection)?


Types of IoC are −

    Constructor-based dependency injection − Constructor-based DI is accomplished when the container invokes a class constructor with a number of arguments, 
    each representing a dependency on other class.

    Setter-based dependency injection − Setter-based DI is accomplished by the container calling setter methods on your beans after invoking a
    no-argument constructor or no-argument static factory method to instantiate your bean.


7. What are the types of IOC container in spring?

There are two types of IOC containers in spring framework.

    BeanFactory
    ApplicationContext

BeanFactory is the basic Spring IoC container. ApplicationContext builds on it and is the one most applications use.

+-----------------------------------+---------------------------------------------+-----------------------------------------------------------------+
| Aspect                            | BeanFactory                                 | ApplicationContext                                              |
+-----------------------------------+---------------------------------------------+-----------------------------------------------------------------+
| Role                              | Basic container for creating and wiring     | Full-featured container that extends BeanFactory                |
|                                   | beans                                       |                                                                 |
| Bean creation                     | Lazy by default: created when first         | Eager by default: singleton beans created at startup            |
|                                   | requested                                   |                                                                 |
| Startup errors                    | Surface later, at first use                 | Surface at startup, easier to catch                             |
| Enterprise features               | Not included                                | Event publishing, i18n message source, resource loading,        |

+-----------------------------------+---------------------------------------------+-----------------------------------------------------------------+

In short, BeanFactory provides the core bean lifecycle and dependency injection. ApplicationContext adds the features needed in real applications. In Spring Boot you always work with an ApplicationContext.

10. How do you define a bean scope?

When defining a  in Spring, you have the option of declaring a scope for that bean. For example, to force Spring to produce a new bean instance each time 
one is needed, you should declare the bean's scope attribute to be prototype. Similar way if you want Spring to return the same bean instance 
each time one is needed, you should declare the bean's scope attribute to be singleton.

11. What are the different bean scopes in spring?

No.	Scope			Description

13. Are Singleton beans thread safe in Spring Framework?

No, singleton beans are not thread-safe in Spring framework. 
It is because the framework creates a singleton bean at the application startup and makes sure that the same instance is autowired and reused in 
all other dependent beans. But the framework doesn't control how the singleton is used. It is developer's responsibility to ensure that the code
runs sqafely in multithreaded environment.

23) What is Component Scan and How to disable Component Scan?


Spring needs to know which packages to scan for annotated components in order to add them to the IoC container. 
In a Spring Boot project, we typically set the main application class with the @SpringBootApplication annotation. 
Under the hood, @SpringBootApplication is a composition of the @Configuration,  @ComponentScan, and @EnableAutoConfiguration annotations.
With this default setting, Spring Boot will auto scan for components in the current package (containing the @SpringBoot main class) and its sub packages.

The @ComponentScan annotation is used with the @Configuration annotation to tell Spring the packages to scan for annotated components. 
@ComponentScan is also used to specify base packages and base package classes using thebasePackageClasses or basePackages attributes of @ComponentScan.

The basePackageClasses attribute is a type-safe alternative to basePackages. When you specify basePackageClasses, Spring will scan the package (and subpackages) 
of the classes you specify.

We can disable Component Scan using excludeFilters.

23) How Is Spring Security Implemented In A Spring Boot Application?

Minimal configuration is needed for implementation. All you need to do is, add spring-boot-starter-security starter in the file pom.xml. 
You will also need to create a Spring config class that will override the required method while extending the WebSecurityConfigurerAdapter to 
achieve security in the application. 

Here is an example code for the same:

package com.gkatzioura.security.securityendpoints.config;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.annotation.web.configuration.WebSecurityConfigurerAdapter;
@Configuration
public class SecurityConfig extends WebSecurityConfigurerAdapter {
    @Override
    protected void configure(HttpSecurity http) throws Exception {
        http.authorizeRequests()
            .antMatchers("/welcome").permitAll()
            .anyRequest().authenticated()
            .and()
            .formLogin()
            .permitAll()
            .and()
            .logout()
            .permitAll();
    }
}

Q. What is Spring Boot profile?

 The development process of an application has different stages; the typical ones are development, testing, and production. 
Spring Boot profiles group parts of the application configuration and make it be available only in certain environments.

A profile is a set of configuration settings. Spring Boot allows to define profile specific property files in the form of application-{profile}.properties. 
It automatically loads the properties in an application.properties file for all profiles, and the ones in profile-specific property files only for the 
specified profile. The keys in the profile-specific property override the ones in the master property file. 

The @Profile annotation indicates that a component is eligible for registration when the specified profile or profiles are active. 
The default profile is called default; all the beans that do not have a profile set belong to this profile. 

There are plenty of ways of defining active profiles in Spring Boot, including command line arguments, Maven settings, JVM system parameters, 
environment variables, spring.profiles.active property, and SpringApplication methods. 

Q. How to run spring boot application to custom port ?

By default, Spring Boot applications run on an embedded Tomcat via port 8080. In order to change the default port, 
you just need to modify the server.port attribute in application.properties, which is automatically read at runtime by Spring Boot applications.

* EmbeddedServletContainerCustomizer:

You can customize the properties of the default servlet container by implementing the EmbeddedServletContainerCustomizer interface as follows:

package com.programmer.gate;

import org.springframework.boot.context.embedded.ConfigurableEmbeddedServletContainer;

import org.springframework.boot.context.embedded.EmbeddedServletContainerCustomizer;

public class CustomContainer implements EmbeddedServletContainerCustomizer {

    @Override

    public void customize(ConfigurableEmbeddedServletContainer container) {

        container.setPort(9090);

    }


}


The port defined inside the CustomContainer always overrides the value defined inside application.properties.


* Command Line

The third way is to set the port explicitly when starting up the application through the command line. You can do this in two different ways:

    java -Dserver.port=9090 -jar executable.jar
    java -jar executable.jar –server.port=9090

The port defined using this way overrides any other ports defined through other ways.

Q. What is circular dependency in spring boot, and how it can be resolved ?

A circular dependency occurs when two or more beans depend on each other, creating a cycle in the dependency graph.
 Spring cannot instantiate these beans because it doesn't know which one to create first.

Q. Spring Bean life cycle

Instantiation: The container creates the bean instance by calling its constructor or factory method.
--------------
Dependency injection: The container populates properties, fields, and setters with their dependencies.
---------------------
Aware callbacks: If the bean implements them, the container calls BeanNameAware.setBeanName(), BeanFactoryAware.setBeanFactory(), and 
----------------
ApplicationContextAware.setApplicationContext().

BeanPostProcessor (before init): postProcessBeforeInitialization() runs on every bean, which is how many framework features hook in.
--------------------------------
Initialization: Spring runs the initialization callbacks in this order:
--------------
	@PostConstruct method
	InitializingBean.afterPropertiesSet()
	Custom init-method (from XML or @Bean(initMethod = "..."))

BeanPostProcessor (after init): postProcessAfterInitialization() runs. This is where AOP proxies are usually created, so the object placed in the context 
-------------------------------
may be a proxy rather than the original instance.

Ready for use: The bean stays in the context and serves requests.
--------------

Destruction: When the context closes, Spring runs the destruction callbacks in this order:
------------
	@PreDestroy method
	DisposableBean.destroy()
	Custom destroy-method

Spring Security Workflow
-------------------------

Spring Security follows a filter-based architecture that intercepts HTTP requests. Here's the core flow:

1. Request Interception

A request arrives and passes through a chain of security filters (managed by FilterChainProxy). Key filters include:

UsernamePasswordAuthenticationFilter (handles login)
ExceptionTranslationFilter (catches security exceptions)
FilterSecurityInterceptor (enforces authorization)

2. Authentication

When credentials are submitted (typically via login):

UsernamePasswordAuthenticationFilter extracts username/password
Creates an Authentication object (unauthenticated)
Delegates to the AuthenticationManager to authenticate

The AuthenticationManager uses AuthenticationProvider(s) to:

Fetch user details (via UserDetailsService)
Compare credentials (using PasswordEncoder)
Return an authenticated Authentication object with granted authorities

3. Session Management

The authenticated Authentication is stored in the SecurityContext
By default, stored in the HttpSession (for web apps)
Subsequent requests retrieve the context from session

4. Authorization

For each protected request, FilterSecurityInterceptor:

Extracts the current Authentication from the SecurityContext
Checks if the user has required permissions/roles
Grants or denies access based on configured rules

5. Response

Success: Request proceeds to the resource
Failure: Exception is thrown → ExceptionTranslationFilter catches it → redirects to login or error page

Key Components
--------------

Component			Role

SecurityContext			Holds the authenticated user
Authentication			Represents credentials/principal
AuthenticationManager		Orchestrates authentication
UserDetailsService		Loads user data from DB/directory
PasswordEncoder			Securely hashes/validates passwords
AccessDecisionManager		Makes authorization decisions
GrantedAuthority		Represents roles/permissions


Typical Login Sequence
-----------------------

HTTP Request → SecurityFilter Chain → 
UsernamePasswordAuthenticationFilter → 
AuthenticationManager → AuthenticationProvider → 
UserDetailsService (load user) → 
PasswordEncoder (validate) → 
SecurityContext stored → Response

JWT Authentication Flow
------------------------

JWT (JSON Web Token) is a stateless, self-contained token that carries user information and can be verified without hitting the database each time.

Structure: header.payload.signature

JWT Structure
--------------

1. Header

Specifies algorithm and token type.

json
{
  "alg": "HS256",    // Algorithm (HS256, RS256, etc.)
  "typ": "JWT"       // Token type
}


2. Payload (Claims)

Contains user data and metadata.

json
{
  "sub": "user123",              // Subject (user ID)
  "name": "John Doe",
  "email": "john@example.com",
  "roles": ["USER", "ADMIN"],    // Authorities
  "iat": 1516239022,             // Issued at
  "exp": 1516242622             // Expiration time
}


3. Signature

Ensures token hasn't been tampered with.

HMACSHA256(
  base64UrlEncode(header) + "." +
  base64UrlEncode(payload),
  SECRET_KEY
)

Q. How is exception handling in spring boot ?


Exception Handling in Spring Boot

Spring Boot provides several mechanisms to handle exceptions gracefully. Here's an overview:

1. @ExceptionHandler

Handle specific exceptions within a controller or globally.

java
@RestController
public class MyController {
    
    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity handleNotFound(ResourceNotFoundException e) {
        ErrorResponse error = new ErrorResponse("Not Found", e.getMessage());
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(error);
    }
}

2. @ControllerAdvice (Global Exception Handler)

Create a centralized exception handler for all controllers.

java
@ControllerAdvice
public class GlobalExceptionHandler {
    
    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity handleNotFound(ResourceNotFoundException e) {
        ErrorResponse error = new ErrorResponse("Not Found", e.getMessage());
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(error);
    }
    
    @ExceptionHandler(Exception.class)
    public ResponseEntity handleGenericException(Exception e) {
        ErrorResponse error = new ErrorResponse("Internal Server Error", e.getMessage());
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR).body(error);
    }
}

3. Custom Exception Class

public class ResourceNotFoundException extends RuntimeException {
    public ResourceNotFoundException(String message) {
        super(message);
    }
}

4. Error Response DTO

@Data
@AllArgsConstructor
public class ErrorResponse {
    private String error;
    private String message;
    private LocalDateTime timestamp = LocalDateTime.now();
}

5. Validation Exception Handling

@ControllerAdvice
public class GlobalExceptionHandler {
    
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity handleValidationException(
            MethodArgumentNotValidException e) {
        String message = e.getBindingResult()
                .getFieldErrors()
                .stream()
                .map(error -> error.getField() + ": " + error.getDefaultMessage())
                .collect(Collectors.joining(", "));
        
        ErrorResponse error = new ErrorResponse("Validation Failed", message);
        return ResponseEntity.status(HttpStatus.BAD_REQUEST).body(error);
    }
}

6. Application Properties Configuration

# application.yml
server:
  error:
    include-message: always
    include-binding-errors: always
    include-stacktrace: on-param
    include-exception: false

Q. Difference between Component and Bean in spring boot


@Component and @Bean are both used to create Spring beans, but they work differently and have different use cases.

@Component
-----------
* @Component is a class level annotation. 
* Spring automatically detects the class through component scanning.
* It is commonly used for classes that er develop such as utility classes.

@Bean
-----
* @Bean is a method level annotation.
* It is generally declared inside a class annotated with @Configuration.
* The method explicitly define how to create and register a bean.
* It is useful when you need to configure third party classes or have control over object creation.


Key Differences
----------------
Feature				@Component			@Bean
--------			----------			-------
Where Applied			On a class			On a method
Automatic Detection	Auto-scanned by Spring			Manual declaration
Class Control		Only on your classes			Can use external/third-party classes
Flexibility		Limited					High (method-based logic)
Configuration		Simple					Needs @Configuration class

@Component
----------
Applied directly to a class - Spring auto-detects and registers it as a bean.

@Component
public class UserService {
    public void saveUser(User user) {
        System.out.println("Saving user: " + user.getName());
    }
}

How it works:

Spring scans for classes with @Component annotation
Automatically creates a bean instance
Registers it in the application context
No manual configuration needed

@Bean
------
Declared as a method inside a @Configuration class - manually defines how to create the bean.

@Configuration
public class AppConfig {
    
    @Bean
    public UserService userService() {
        return new UserService();  // You control instantiation
    }
}

How it works:

Define a method inside @Configuration class
Method returns an object
Spring calls this method and registers the return value as a bean
Gives you full control over bean creation

Q. What is Spring AOP ?

Spring AOP (Aspect-Oriented Programming) is a framework that implements cross-cutting concerns such as transactions, logging, security, and caching by creating proxy objects around Spring beans. The proxy intercepts method calls and executes additional behavior before, after, or around the target method without modifying the business logic.

---------------------------------------
Annotation	Purpose
----------	--------
@Transactional	Transaction management
@Cacheable	Caching
@Async		Asynchronous execution
@PreAuthorize	Security checks
@Retryable	Retry failed operations
Custom Aspects	Logging, auditing, monitoring

Q. How @Transactional works internally ?

@Transactional in Spring internally relies on AOP (Aspect-Oriented Programming), dynamic proxies, and a transaction manager.

@Transactional works by letting a Spring AOP proxy intercept method calls, start a database transaction through PlatformTransactionManager, bind the connection to the current thread, execute the method, and then commit or roll back depending on whether an exception occurs.`

1.Spring creates a proxy around the bean containing @Transactional.
2.When the method is called, the proxy intercepts the call.
3.The proxy asks the TransactionManager to start a transaction.
4.A database connection is obtained and autoCommit is set to false.
5.The connection is bound to the current thread, so all database operations use the same transaction.
6.The target method executes.
7.If the method succeeds:
8.COMMIT is executed.
9.If an exception occurs:
10.ROLLBACK is executed (by default for unchecked exceptions).



Q. Why might @Transactional not work when calling from the same class ?

    - Self invocation can bypass Spring's proxy, so the transactional interceptor may not be triggered.


Q. If a private method is annotated with @Transactional, will it work at runtime?

              No, it will not work. Spring AOP uses dynamic proxies (either JDK dynamic proxies or CGLIB) to manage transactions.

Visibility Constraint: Spring's proxy framework only intercepts public method invocations. 
If a method is private, the proxy logic cannot wrap around it, and the @Transactional annotation is silently ignored.

Self-Invocation Issue: Even if a method is public, calling it internally from another method within the same bean bypasses the proxy entirely, meaning the transaction context will not be applied.

Q. What are the steps when a Spring Boot application starts?

	 The initialization of a Spring Boot application (SpringApplication.run()) follows a highly structured lifecycle:

1. Bootstrap & Environment Setup: 
   Prepares the ConfigurableEnvironment, loads application properties, system variables, and active profiles (e.g., application.yml).
2. ApplicationContext Creation:
   Instantiates the appropriate ApplicationContext based on the application type (e.g., AnnotationConfigServletWebServerApplicationContext for web apps).
3. Bean Definition Loading: 
   Scans the classpath (@ComponentScan) to find components, configurations, and controllers, registering their BeanDefinitions.
4. Context Refresh & Bean Instantiation: 
   Executes refreshContext(). This is where core Spring lifecycle steps happen—invoking bean factory post-processors, initializing the bean post-processors, and instantiating singleton beans (including REST controllers and database drivers via dependency injection).
5. Embedded Server Startup: 
   If it's a web application, it starts the embedded servlet container (e.g., Tomcat, Jetty).
Runners Execution: Executes any beans implementing CommandLineRunner or ApplicationRunner.

	Spring provides several mechanisms to handle ambiguous dependencies:

Q: What does component scan do?

Answer: Component scanning is the mechanism Spring uses to automatically discover and register beans:
Directive: Triggered by the @ComponentScan annotation (implicit within @SpringBootApplication).
Package Scanning: It recursively scans the base package and its sub-packages.
Stereotype Detection: It looks for classes annotated with @Component, @Service, @Repository, or @Controller.
Metadata Creation: For every matching class found, Spring creates a BeanDefinition and registers it within the Application Context so it can be managed and injected.

Q. How does the application context get bootstrapped and initialize all the dependencies when Spring Boot starts up?

Answer: The startup process follows these core phases:

1.Entry Point: Execution begins at the @SpringBootApplication class via SpringApplication.run().

2.Environment Preparation: Spring creates and configures the Environment (loading application.properties, YAML, and system environment variables).

3.Context Creation: The ApplicationContext (usually AnnotationConfigServletWebServerApplicationContext for web apps) is instantiated.

4.Bean Definition Loading: Component scanning finds bean definitions, and auto-configuration triggers look for metadata in META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports

5.Context Refresh: Spring iterates through bean definitions, resolves dependencies, instantiates the singleton beans, and injects them (Dependency Injection).

6.Embedded Server Startup: The embedded servlet container (like Tomcat) is initialized and started.

Q: What are all the different steps that happen within Spring Boot itself when a consumer makes a request to the controller?

Answer: The request lifecycle follows the Front Controller pattern:

Tomcat/Server: Receives the HTTP request and routes it to the DispatcherServlet.

Handler Mapping: DispatcherServlet queries HandlerMapping to find the appropriate Controller and method matching the URL route.

Interceptors: The request passes through any configured HandlerInterceptor chains (executing preHandle tasks like auth check or logging).

Handler Adapter: DispatcherServlet uses a HandlerAdapter to dynamically invoke the actual controller method.

Controller Execution: The controller processes the request, calls the service layer, and returns the response payload.

Response Handling: The return value is processed by HttpMessageConverter (e.g., converting a Java object to JSON via Jackson) and sent back through the interceptors (postHandle/afterCompletion) to the consumer.

Q: What are all the different levels of testing that you have been doing or that you know that are required?

Answer: Enterprise applications require a comprehensive testing pyramid:

Unit Testing: Testing isolated blocks of code (individual methods) using mocks (Mockito) for external dependencies.

Integration Testing (@SpringBootTest): Verifying the interaction between multiple layers or modules (e.g., testing the Service layer with a real database or an H2 in-memory DB via @DataJpaTest).

Component/Contract Testing: Verifying that API endpoints adhere to exact input/output structures (schemas) without testing full end-to-end setups.
End-to-End (E2E) Testing: Testing the entire system flow from the frontend/API gateway down to the actual database and third-party systems.

Q: What is the difference between unit testing and functional or end-to-end testing, and what are developer responsibilities?

Answer:

Unit Testing: Focuses on the smallest testable parts of an application (methods/classes) in absolute isolation. It uses mock objects to simulate external systems.
Functional / End-to-End Testing: Tests the application from a user's perspective, verifying that business features function correctly across multiple integrated systems (databases, message queues, external APIs).
Developer Responsibilities: Developers are directly responsible for writing Unit and Integration tests as part of the CI/CD pipeline. They must ensure high code coverage and block regressions before code reaches QA or user acceptance testing (UAT).

Q12: Other than Singleton, can you give me a design pattern that you've used and explain how it works and its use cases?

Answer:

Factory Pattern:
How it works: Defines an interface or abstract class for creating an object, but lets subclasses or a dedicated factory class decide which concrete class to instantiate.
Use Case: Dynamic implementation loading. For example, creating a PaymentFactory that returns either a CreditCardPaymentProcessor or a PayPalPaymentProcessor bean at runtime based on the user's choice.

Builder Pattern:
How it works: Separates the construction of a complex object from its representation, allowing step-by-step object creation.
Use Case: Generating immutable DTOs or Entity objects with many fields without creating bloated constructors (frequently achieved using Lombok's @Builder).

Q13: Can you walk me through the repository service controller pattern?

Answer: 
This is the standard layered architecture pattern designed to enforce separation of concerns:

Controller Layer: The entry point. It handles HTTP routing, parameter binding, request validation, and returns the appropriate HTTP status codes and DTO responses. It contains no business logic.

Service Layer: The core engine. It implements the actual business logic, orchestrates workflows, manages data transformations, and coordinates transactions (@Transactional).

Repository Layer: The data access layer. It abstracts database communication (using frameworks like Spring Data JPA or MyBatis) to execute CRUD operations and complex queries against the underlying database.


Q14: Have you used any ORM frameworks and how does that influence code writing?

Answer:

 Yes, frameworks like Spring Data JPA (Hibernate) or MyBatis significantly streamline development:

Abstraction of SQL: Developers work directly with Java objects (Entities) rather than writing raw, error-prone SQL strings for basic operations.

Automated Lifecycle Management: Features like automatic dirty checking, caching, and relationship mapping (@OneToMany, @ManyToOne) reduce boilerplate code.

Influence on Code: Code becomes much cleaner, more object-oriented, and less coupled to a specific database vendor (easier database migrations). However, developers must remain mindful of performance traps like the N+1 select problem.


Q15: How do entities and DTOs relate, why is there separation, and would you return raw entities to the response?

Answer:

Definitions: Entities map directly to database tables, while DTOs (Data Transfer Objects) map directly to API request and response payloads.

Why Separate?

Security: Entities may contain sensitive fields (e.g., passwords, internal IDs, audit timestamps) that should never be exposed to the client.

Decoupling: Decouples the database schema from the external API contract. Changes to database tables won't break client applications.

Performance & Structure: APIs often require data in formats different from how they are stored in a database (e.g., aggregations or flattened fields).
Should you return raw entities? No. It is a security risk, creates tight coupling, and often leads to infinite serialization loops if entities have bidirectional relationships.
